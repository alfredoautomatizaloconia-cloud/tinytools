Why MCP Configs Fail Silently

MCP servers are spawned as child processes by your AI client. If the JSON is malformed, the path is wrong, or the environment variables are missing, the client typically just… doesn't spawn the server. No warning. No red error box. The tools just aren't there.

This is by design — clients treat MCP servers as optional enhancements, not core dependencies. But it means the feedback loop for debugging is brutal. You edit the config, restart the client, open a new chat, try to call a tool, get nothing, repeat. Average debug time for a first-time MCP setup: 2–4 hours.

Here are the five mistakes responsible for ~85% of broken setups:

Mistake #1 — Most Common

Wrong config file location (or wrong client format)

Every MCP client stores its config in a different place and uses a slightly different JSON structure. Claude Desktop, Cursor, Cline, Continue, Windsurf, and Zed all have different file paths and different key names.

Mistake #2 — Runner-up

Using npx without the full binary path

This is the most maddening one. It works fine when you run it in your terminal. It fails silently inside the MCP client. The reason: AI clients often launch with a minimal PATH that doesn't include your Node.js installation.

{
  "command": "npx",   // ← FAILS inside Claude Desktop / Cursor
  "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/you/Desktop"]
}
✓ FIX

Use the absolute path to npx. Run which npx in your terminal, then paste the full path:

{
  "command": "/usr/local/bin/npx",   // ← works reliably
  "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/you/Desktop"]
}

On Windows: find it with where npx and use forward slashes or escaped backslashes in the JSON.

Mistake #3

Missing or wrong env block for API keys

Many MCP servers (GitHub, Slack, Linear, Notion, Postgres) need API tokens or connection strings. The correct way to pass them is via the env block in the config — not as args. But which key name does each server expect?

{
  "github": {
    "command": "/usr/local/bin/npx",
    "args": ["-y", "@modelcontextprotocol/server-github"],
    "env": {
      "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_your_token_here"
    }
  }
}

The env key name must match exactly what the server expects. GITHUB_TOKEN vs GITHUB_PERSONAL_ACCESS_TOKEN — wrong name, silent failure. Every server is different.

Mistake #4

Trailing commas in JSON (it's not JavaScript)

JSON does not allow trailing commas. Most editors will catch this, but if you're editing the config file directly or copying from a forum post, a single trailing comma will break the entire config.

{
  "mcpServers": {
    "filesystem": {
      "command": "/usr/local/bin/npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],  // ← invalid JSON
    },  // ← also invalid
  }
}
✓ FIX

Always validate your JSON before saving. Paste it into jsonlint.com, or better yet — generate the config with a tool and never hand-edit it.

Mistake #5

Forgetting to fully restart the client

This sounds obvious but it's responsible for ~20% of "my config isn't working" support requests. Claude Desktop, Cursor, and most other clients only reload their MCP config on full application restart, not on window close or new chat. On macOS, "Cmd+Q → reopen" is not always a full quit — use the menu bar or Dock right-click → Quit.

✓ FIX

On macOS: Cmd+Q to quit, then reopen. On Windows: close all windows, check the system tray. Alternatively, look for a "Reload MCP servers" command in the client's developer/debug menu.

The Difference Between a Broken and a Working Config

Here's a complete working example for Claude Desktop with three popular servers (Filesystem, GitHub, and Postgres) so you can see how all the pieces fit together:

{
  "mcpServers": {
    "filesystem": {
      "command": "/usr/local/bin/npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem",
               "/Users/yourname/Documents", "/Users/yourname/Desktop"]
    },
    "github": {
      "command": "/usr/local/bin/npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_..."
      }
    },
    "postgres": {
      "command": "/usr/local/bin/npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres",
               "postgresql://localhost/mydb"]
    }
  }
}

Notice: absolute path for npx, correct top-level key mcpServers, no trailing commas, env block only where needed, and args are an array — never a string.

How Many MCP Servers Should You Actually Run?

People see a list of 40+ MCP servers and want to enable everything. Resist this. Each server is a spawned process with its own startup time and potential failure point. Practical rule of thumb:

  • 1–3 servers: instant startup, highly reliable
  • 4–8 servers: noticeable startup delay (~2–5s), manageable
  • 9+ servers: slow startup, higher chance of one breaking silently

Start with the servers that actually match your workflow. If you're a solo developer, Filesystem + GitHub + your database covers 90% of use cases. Add more only when you hit a specific need.

What's Coming in MCP Next

MCP is still in its early days. A few things worth watching in the next 6 months:

OAuth for MCP servers — right now, most servers use long-lived API tokens stored in plaintext in your config file. The MCP spec is actively working on OAuth flows that would replace static tokens with short-lived credentials. This will change the config format significantly.

Remote MCP servers — today almost all MCP servers run as local processes. The spec supports remote HTTP servers, and we're starting to see hosted MCP services emerge. This will make config simpler but introduces new latency and trust considerations.

Config management tools — the fragmented per-client config situation won't last. Expect consolidated config managers, possibly baked into AI clients themselves, within the next year.

For now, the fastest path to a working MCP setup is still: generate a correct config, use absolute paths, and restart properly. That eliminates 90% of issues.
